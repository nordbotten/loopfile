# A step field takes its value from data through a JS template string, with no eval, and a profile gives a step its base fields

A Loopfile that picks a model for each task, for example a cheap lane for easy work and a strong lane for hard work, needed one copy of a step for each lane, because `model`, `effort` and `harness` were fixed text. We let a step field take its value from data at call time, and we let a step take its base fields from a named profile that data can pick. A field expression changes one value inside one harness. A profile changes the whole set, harness included, and every profile is written by the author and checked before the run. We picked a JS template string parsed with `jsep` and walked by our own code, not `eval`, because a Loopfile can be remote (ADR 0013). The map is nordbotten/loopfile#226, and every bare ticket number here is in nordbotten/loopfile. The detail of each decision is in the ticket it cites. This ADR records what they are and how they fit.

## Decisions

- **Which fields (#229, #242):** `model`, `effort` and each item of `profile` accept a field expression, on every step that has them. `harness`, `args` and the limits are never field expressions. `harness` changes only through a profile.
- **Form (#230):** the loader reads the field value as the text of a JS template string and adds the backticks itself, so `model: opus` stays the text `opus`. `${ <expression> }` fills in a value, for example `model: claude-${triage.size}` or `model: ${triage.model ?? "opus"}`. `\${` gives a real `${`. A value that starts with a backtick is a load error with the help text "leave out the backticks". A ternary needs YAML quotes or a `>-` block.
- **Expression (#230):** allowed are names, text in single or double quotes, numbers, `true`, `false`, `! && || ?? == != === !== < > <= >= + * / % ? :` and parentheses. Refused at load: function calls, `[ ]` access, `this`, arrays, objects, and `??` with `||` in the same expression, because `jsep` drops parentheses. `-` is a name character, as in `implement-easy`, so there is no minus. The expression works exactly as in JS, and data values are text.
- **Source (#230):** only data keys, `input.<name>` and `<step>.<output>`. A name gives the newest value. `$history` and `$run` cannot be used. A route carries no value.
- **Result (#230):** a `${ }` that gives `undefined` fails the attempt before the call with `bad_field`, and the run takes `onFailure`. In a Ralph step, the whole attempt fails. Any other value becomes text, as with `String()`, and `""` passes on as `""`. To get the default of a field, leave the field out.
- **When (#230):** the fields are filled before each harness call, like the prompt, so a Ralph iteration sees what earlier iterations put.
- **Engine (#230):** `jsep` 1.4.0 and `@jsep-plugin/template` parse the field, with `-` added as a name character. About 30 lines of our own code walk the tree, and the loader walks the same tree for its checks. There is no `eval`. Prompts stay Handlebars (ADR 0012).
- **Profiles (#242):** `profiles: { <group>: { <name>: <part of a step> } }`, always two levels, so a name is always `group.name`. A step names one profile or a list, for example `profile: [review.base, implement.${triage.complexity ?? "medium"}]`. The profiles merge left to right, then the step's own fields apply. Each field is replaced whole, so lists are not joined. A step cannot unset a field that a profile sets. A profile cannot hold `id` or `profile`.
- **Filled profile (#242):** a profile name from a field expression must start with a fixed `group.`. Such a profile can set only the fields read at each call: `harness`, `model`, `effort`, `args`, `prompt`, `promptFile`, `timeout` and `run`. It cannot set `kind`, `on`, `onFailure`, `outputs`, `maxAttempts` or `maxIterations`, because these make the graph or count over many calls, and the loader and other steps need them at load. A field expression inside a profile is allowed.
- **Load checks (#231, #242):** the loader checks the form of a field, not its value. Each name in a `${ }` must be a declared input or a declared step output, with no order check, as for prompt placeholders. The loader does not check the text inside an expression. A profile alone gets a small check of its field names and types. The full check is each step with its profiles merged, as if written inline, and for a filled profile once for each profile in its group. A field expression inside a profile is checked in the step that uses it. A fixed profile name must exist. A fixed `effort` is checked against the harness words. `model` is never checked. A profile that no step uses gets only the small check.
- **Call-time checks (#231, #242):** a filled `effort` is checked against the harness words before the call, because claude and pi both accept a bad word, use the default effort and exit 0. A filled profile name that is not in its group fails. Both fail the attempt with `bad_field`. Where the harness words come from can change with #240.
- **Events (#232, #242):** `attempt.started` of an agent step and `iteration.started` of each Ralph iteration get an optional `fields` map. The `attempt.started` of a Ralph step has none. The map holds `profile` when the step has one, and the `harness`, `model` and `effort` of the call. A field the step leaves out is not in the map. The other profile fields are fixed text that the profile name finds in the Materialized Loopfile. The map is optional, so the event format version stays `1` (ADR 0006).
- **A failed fill (#232):** a new `AttemptEndReason`, `bad_field`. `attempt.ended` gets `field` and `value`, with no `value` for `undefined`. An agent step writes `attempt.started` with `processGroupId: 0` and then `attempt.ended`, as for `start_failed`. A Ralph step writes no `iteration.started`.
- **Prompt data and status (#232, #242):** `$run.attempt.fields` holds the values of the current call, and `$run.attempts[].fields` holds the values of the last call of each earlier attempt (ADR 0005). The fields are filled before the prompt. `current.harness` in `status.json` comes from the `fields` map of the current call, and it is `null` before the first fill.
- **Trust prompt (#233, #242):** a field expression shows as written, for example `claude ${triage.model ?? "opus"}`, with no marker. The step line shows `effort` in parentheses: `claude opus (high)`, `claude - (high)` or `claude -`. A step with a profile shows `profile` as written. A new "Profiles" part lists each profile once, with its harness, model, effort, full `args` and the first line of `run`. There is no new warning, because only the Loopfile's own steps and the user's inputs put the data (#107).
- **Where the values show (#241, #242):** plain `tail` shows the `fields` map in map order, for example `step started profile implement.high harness claude model claude-opus-5-5 effort high`, and a new `iteration <n> started …` line for each Ralph iteration (ADR 0007). A failed fill shows as `step ended bad field effort "hgih"` or `step ended bad field model`. `result --json` gets `lastOutcome.fields`, and the plain line shows the same values. `list` does not change.
- **Format version (#242):** no bump. An old tool refuses `profiles:` as an unknown field. It takes `model: ${…}` as text, and the call then fails. There are no users yet.

## Considered Options

- **Handlebars `{{ }}` in step fields:** one syntax for prompts and fields, but a field needs operators such as `??` and `?:`, and Handlebars has none without custom helpers (#230, ADR 0012).
- **`eval` or `new Function` for the expression:** less code, but a Remote Loopfile could then run any JS in the run owner (#230).
- **A `with:` on a route that carries a value:** the value would live in the graph, not in the data (#230).
- **`harness` as a field expression, with an `args` map for each harness:** pi 0.87.1 refuses a flag it does not know, such as claude's `--settings`, so one `args` list cannot serve two harnesses. The effort words also differ by harness. A profile keeps each harness set fixed and checked at load (#242).
- **`args` and the limits from data:** `args` can change permissions, and an agent could remove its own limit (#229). A profile only picks among values the author wrote.
- **YAML merge keys (`<<: *base`):** fixed at parse time, so they cannot pick from data, and the `yaml` package needs `merge: true` for them (#242).
- **A profile that names other profiles:** chains need a check for loops. A step lists its profiles instead (#242).
- **One flat set of profiles:** a filled name would be checked against profiles made for other steps (#242).
- **A `(from data)` marker in the trust prompt:** it hides the expression (#233).
- **A format version bump:** every current manifest would get the upgrade prompt for a case with no users (#242).

## Consequences

- `jsep` and `@jsep-plugin/template` join the runtime dependencies that `CORE` imports.
- A typo in a literal inside an expression, such as `?? "meduim"`, shows only at call time.
- A step has two ways to say its harness: its own `harness` field, or a profile.
- The `effort` words come from the fixed harness table until #240.
