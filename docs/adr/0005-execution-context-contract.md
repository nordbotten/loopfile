# Steps get one execution context through environment variables

Every attempt, of every step kind, gets the same execution context: a small set of `LOOPFILE_*` environment variables. The runtime builds the context as logical values. The executor turns each value into what the process sees: a real path for a local process, and later a mount path for Docker. Steps read inputs and publish data only through Loopfile's data and result commands, which send each call to the run owner. We picked this so a new executor only changes how values are mapped, never what a step or harness adapter sees, and so every read and write a step makes is an event.

## Decisions

- **Same for all step kinds:** agent, command and Ralph steps get the same context. A shell script in a command step reports its outcome with the same result command as an agent.
- **Variables only:** the context is passed only as environment variables. There is no context file. The helper CLI never finds its run from the current directory.
- **Contents:**
  - `LOOPFILE_RUN_ID` and `LOOPFILE_ATTEMPT_ID` (for example `007-fix`) and `LOOPFILE_STEP`.
  - `LOOPFILE_PROTOCOL_VERSION`: the integer version of this contract (ADR 0006). It is a version, not the name of a transport, so the long form is used.
  - `LOOPFILE_WORKSPACE`: the workspace root. It is also the process's working directory.
  - `LOOPFILE_SCRATCH`: a writable folder in the attempt folder, for temp files the step must not commit. Nothing in it is collected. Like the rest of the attempt folder, it does not change after the attempt ends.
  - `LOOPFILE_ENDPOINT`: an opaque value the data and result commands use to reach the run owner.
  - `LOOPFILE_ATTEMPT_SECRET`: a random value made for each attempt. A Ralph step gets a new one for each iteration.
- **Inputs:** a step gets no path to the materialized Loopfile. Handoffs are read through the data commands, so every read is an event and a Docker executor needs no mount for them. The harness adapter runs in the run owner and gives the prompt to the harness itself.
- **No static asset reader in v1 (#84):** there is no `asset get` command and no reserved key prefix. Prompts are the only static assets a v1 Loopfile ships, and the adapter already reads them in the run owner, so no step can call such a command. It returns with the first asset a step must read itself, as a separate command rather than a prefix, so the flat data key space stays flat.
- **Latest value only (#84):** `data get <key>` returns the newest value. There is no `--attempt` flag and no `data history` command; earlier values are read from `events.jsonl` by readers, not by steps. `data get` does print the attempt ID that put the value on stderr, next to the `bytes:` line of #83, so a step can tell a fresh value from a carried-over one. This holds for steps only. A prompt can read every value of a key and the run facts through prompt data (#244), because the run owner fills it as a reader of `events.jsonl`.
- **Prompt filling (#96):** the run owner fills `{{ <data key> }}` placeholders in the prompt text before the harness adapter hands it to the harness, once per harness call, so each Ralph iteration sees what earlier iterations put. The prompt is a Handlebars template over prompt data (#241, #244, ADR 0012): the inputs under `input.<name>`, the handoffs under `<step>.<output>`, the value history of each key under `$history.<key>`, and the run facts under `$run`. In a Ralph step, `$run.attempt` also gives the iteration number, the iteration limit and how the iteration before ended, while `$run.previous` and the `new` flag of a history entry stay counted per attempt, not per iteration (#250). `$run` also gives the run facts of `loopfile result --json` with the same names, the earlier attempts of the run as `$run.attempts` (without their handoffs, which `$history` has), the limits of the step and the run with the counts so far, and the flags `lastAttempt` and `lastIteration`, because a prompt cannot compare numbers (#255). A step ID must start with a letter, so the `$` roots can never clash with a step, and no step ID is reserved for them (#245). A block can repeat or leave out text, but there are no custom helpers, so a prompt holds no code. A list or map used as a plain placeholder fills as JSON. The loader checks every name a prompt reads, inside blocks too, and refuses the features ADR 0012 lists. A plain `{{ <data key> }}` fills as before: a put key as its newest value and an appended key as its whole value history, which the run owner joins as a reader of `events.jsonl`, not through a step command. A key with no value yet fills as an empty string, which the `prompt.filled` event records (ADR 0003).
- **Publishing:** data is published only with an explicit data command that copies the content. Declared outputs (#22) are checked as required data keys at attempt end, not collected from a folder.
- **Transport:** only the helper CLI and the run owner know what is behind `LOOPFILE_ENDPOINT`. In v1 it is a Unix socket in the attempt folder. The harness adapter adds the socket and the scratch folder to the harness sandbox allowlist through its wiring files. This holds for the v1 harnesses, Claude Code and PI (#89), neither of which sandboxes a step's own processes.
- **Old attempts:** the run owner accepts a call only when its attempt ID and secret match the attempt that is running now. For a Ralph step, the secret must also match the iteration that is running now. Other calls get an error. This stops processes left over from ended attempts and iterations. It is not a security boundary, because the agent can read its own environment.

## Considered Options

- **Extra context for agent steps:** command and agent steps would report outcomes in different ways.
- **Context JSON file in the attempt folder:** one more file that a Docker executor must mount and keep in step with the variables.
- **Read-only path to the materialized Loopfile:** simpler for static assets, but those reads would never be events, and Docker would need a mount.
- **An `asset get` command in v1:** a command with no caller, because the adapter reads the only static assets there are.
- **A reserved key prefix for assets:** one command instead of two, but it mixes a path space into the flat key space and needs a reserved-prefix rule.
- **`data history` and `data get --attempt`:** two more surfaces to build and version for a step that can use two data keys instead. A prompt does not need them either: it reads history and run facts through prompt data (#244).
- **Cap or cut prompt data, per value or per prompt:** a cut changes what a value means, and the useful part differs by key, such as the tail of a test log and the start of a review. It also needs a new Loopfile field and a mark for a cut value. A block can already show only the newest entry or only the new ones, so the prompt author controls the size (#258).
- **Collect declared outputs from a writable output folder:** a second way to publish next to the data commands.
- **Helper CLI writes data or events itself:** breaks the one-writer rule of ADR 0003.
- **Inbox folder with request and reply files instead of a socket:** works in every harness sandbox without a socket allowlist, but needs polling. Kept as the fallback.

## Consequences

- **The Codex CLI cannot use this transport.** Tested under its default Linux sandbox (#88): `connect` is blocked for every address family, `AF_UNIX` included, and the only setting that lifts the block, `sandbox_workspace_write.network_access`, opens the full network. There is no socket-only allowlist. Codex is therefore out of the v1 harness table (#89). Adding it later means switching to the inbox folder fallback above and giving the adapter a sandbox write allowlist for the attempt folder (`sandbox_workspace_write.writable_roots`), because Codex mounts everything outside the workspace read-only. The contract does not change, only the transport behind `LOOPFILE_ENDPOINT`. Work in progress for that path is on branch `worktree-wf-88-socket-test`.
- Gemini CLI's Docker sandbox passes only a fixed list of environment variables. Its adapter must add the `LOOPFILE_*` variables with `SANDBOX_ENV`.
- The data commands (#19, #20) read data keys only. A later static asset reader is an addition to this contract and bumps `LOOPFILE_PROTOCOL_VERSION` only if it changes something a step already relies on.
- ADR 0004 says a harness adapter gets prompt file paths. The adapter reads them in the run owner. It never passes a materialized Loopfile path to the harness.
