# Run state is an append-only event log with one writer

The source of truth for a run is `events.jsonl`: an append-only file with one JSON event on each line. Current run state is built by replaying the events. We picked this over a `state.json` that is changed in place plus attempt records that never change, because a crash between those two writes leaves them out of step, and because the activity log, the status projection and resume all need one ordered feed of facts. Runs have hundreds of events, so replay is cheap.

## Loops

A loop has its own append-only `events.jsonl` under `loops/<loopid>/`, separate from every child run. The loop owner is its one writer; readers derive loop status by folding that log, and the same append path writes each event with `fsync`. `loopfile resume <loopid>` takes over a crashed loop by appending a new `owner.started` and replaying the log. The fold restores the input-source place, run count and retry chain. A still-running child is waited for, a completed child advances the source, and a logged child with no run folder is started with its recorded run ID and input set. On resume, a crashed or `internal_error` child is resumed first; `--kill-leftovers` is passed through, and a refused child resume ends the loop with that error summary. A failed child uses the logged retry limit, a cancelled child ends the loop as cancelled with detail naming the run and no cancel mode, and a pending loop cancellation is honoured before another run starts. While its owner is alive, a child crash still ends the loop with `internal_error` (#59).

## Decisions

- **Location:** `~/.loopfile/runs/<runid>/` on Linux and macOS. `LOOPFILE_HOME` overrides `~/.loopfile`.
- **What is an event:** a state change (run created, attempt started and ended, outcome, route taken, run ended) or a step's call to Loopfile's data layer (`data.get` and `data.put`). Harness activity such as tool calls, tokens and progress text is not an event. It goes only to the activity log. Live harness progress remains outside the event log, but an attempt's final metrics are part of its `attempt.ended` event. A terminal event may also carry the final metrics snapshot so `tail --json` can expose the same run metrics.
- **Data layer events:** each one is named after the command that made it, so a put is `data.put` and a get is `data.get`, whatever the key holds (#93). They record the call name, the key, the byte size and a content digest. They never record the content.
- **Event envelope:** each event has a `seq` number that goes up by one for each event, a timestamp and a type. The first event, `run.created`, records the event format version. The rules for reading older versions belong to the versioning decision (#59).
- **Workspace in `run.created` (ADR 0014):** every run records `workspacePath` and `workspaceMode`. Runs with a Target folder record `targetFolder`; `empty` runs do not. An `isolate` run also records `isolateKind` as `worktree` or `copy`. Only an `isolate` worktree records `branch` (`loopfile/<runid>`) and `baseCommit`, the Target folder's `HEAD` at launch. The event log holds the commit the run actually started from, even after `HEAD` moves (#87).
- **One writer:** only the run owner, which is the process that runs the steps, appends to `events.jsonl`. `status`, `list`, `tail`, the monitor and all other processes only read it. Readers never repair or change it.
- **Cancel:** `loopfile cancel` asks the run owner to stop. The run owner writes the cancelled event and exits. How the request is sent is decided in #61.
- **Crashed:** is never written. A reader shows a run as crashed when the log has no end event and the recorded run owner is not alive.
- **Loopfile's own errors:** when an error escapes the run owner, it appends `run.ended` with the result `failure` and the reason `internal_error` before it exits, so a bug in Loopfile does not read as a crash. The write is best effort: if it throws too, the owner exits and the run reads as crashed, which is what SIGKILL, a full disk and a broken log leave behind anyway. The message stays in `owner.log`, which `loopfile logs <runid> --owner` prints (#196).
- **Resume after `internal_error`:** it is the one end reason resume accepts. The run's branch and attempts are still worth continuing, and our bug should not cost them. Resume refuses when the last event is a second `run.ended` with reason `internal_error` and no `attempt.started` between the two, so a bug that fires every time cannot loop (#196).
- **Resume after a loop `internal_error` (#80):** `resume <loopid>` also accepts a loop ended by an escaping driver error. Its `loop.ended.childSeq` records the last readable child event sequence, or `null` when no child event is readable. Resume refuses when two `loop.ended` events with reason `internal_error` have the same `childSeq` and no `loop.run_started` between them; report that as a bug and start a new loop. A `loop.run_started` or a changed child sequence proves progress. The new `owner.started` clears the prior internal-error end in the status fold so replay can continue the loop.
- **Continue after an end:** an ended run is final unless a person continues it with `loopfile continue`. It accepts every end except `completed` and `internal_error`. The run owner appends `run.continued` and starts a new attempt of the step that stopped the run. It writes no transition, so the attempt gets the same inputs, as after an interrupt. When a limit refused the last move, it takes that move instead. `maxAttempts`, `maxTransitions` and `runTimeout` count from the last `run.continued`. A person asks for each continue, so this cannot loop without end. `resume` stays only for Loopfile's own failures (#85).
- **Big data:** handoff contents, harness output and step results are kept in `runs/<runid>/attempts/<nnn>-<step>/` (for example `007-fix`). The number counts attempts across the whole run and is the attempt ID used in events. Nothing in an attempt folder changes after the attempt ends. Events only point to these files.
- **Handoffs:** a handoff is a plain data key (#72), so its put is a `data.put` event like any other. Each put makes a new value that belongs to its attempt. The value a reader gets is the one from the last `data.put` for that key. Earlier values are kept. `loopfile data append` writes a `data.put` too and marks the key as an appended key, so a reader that wants every value for the key can join them oldest first (#96). The `appended` mark decides only what a plain placeholder for the key fills. Prompt data gives the value history of every key (#244), so a key must still not mix `put` and `append`.
- **Prompt fill:** the run owner records one `prompt.filled` event each time it fills a prompt's placeholders for a harness call. It records the step, the attempt, the iteration, every data key it read, whether each key had a value, the value histories and run facts it read as an optional field (#243), the byte size of the filled text and its digest. The step makes no call, so without this event the read would be invisible (#96). The run owner never caps or cuts prompt data: the prompt author picks which values a prompt shows, and a prompt too large for the model fails in the harness like any other harness error. The byte size lets an operator see a prompt grow across attempts before that happens (#258).
- **Safe writes:** each event is one append-mode `write` followed by `fsync`. A reader skips a broken last line. A broken line in the middle means the run is corrupt, and resume stops with an error.
- **Resume after a crash:** if an attempt has a start event but no end event, the run owner appends `attempt.interrupted` and starts a new attempt from the beginning. It never continues the old attempt.
- **Attempt limit:** an interrupted attempt counts toward the step's `maxAttempts`, whatever interrupted it — a crash or `loopfile cancel`. The replay rule is one line: a step's attempt count is the number of `attempt.started` events for that step after the last `run.continued`. When the count is already at `maxAttempts`, resume writes `attempt.interrupted` for the unfinished attempt and then ends the run with the reason `attempt_limit` instead of starting a new attempt.
- **Removal (ADR 0014):** a run folder is deleted only by `loopfile remove <runid>` or `loopfile prune`, never by age or on Loopfile's own initiative. A successful run attempts to remove its isolate worktree; if Git refuses, it stays and the reason is reported. Removal is not a write to the event log, so it does not break the one-writer rule, but it refuses a run whose owner still answers or whose attempt left processes behind. A `here` run's Target folder is never removed. Removing an isolate copy or an `empty` workspace deletes that folder; uncommitted work in an isolate worktree stops removal unless `remove --force` passes `--force` to git. `prune` never forces. The run branch is never deleted. `prune` takes only runs that ended and cannot be resumed; a crashed run or an `internal_error` run is removed one at a time, because deciding not to resume it is a caller's choice (#197).
- **No snapshot:** no built state file is saved. If replay ever becomes slow, a snapshot can be added as a cache that records the last `seq` it includes and can be rebuilt at any time. This does not change the event format.

## Considered Options

- **Mutable `state.json` plus attempt records that never change:** easier to read, but two writes can get out of step after a crash, and observers would have no ordered history to build from.
- **Do not count an interrupted attempt:** a machine crash would not use up a retry, but replay would have to subtract interrupted attempts, and a step that kills the run owner every time could loop without end under a supervisor that keeps resuming.
- **Let `resume` accept every end:** one command, but `resume` means that nothing about the run changes, and it refuses a changed model. Continuing after a failure is a person's choice, so it gets its own verb and its own limit rule (#85).
- **Continue as a new run from the old run branch:** keeps every run final, but splits one piece of work across two run IDs, and the new run loses the attempt history and data that its prompts read.
- **A `reason` field on `attempt.interrupted` so a cancel does not count:** one more branch to save one retry in a rare, deliberate act. Add it later if it bites.
- **A separate `handoff.put` event:** a second name for one call, with no rule for which key earns which name. #72 made a handoff a plain `data put`, so the difference would live only in the log.
- **Record harness activity as events:** a lot of noise that resume and routing never use.
- **Record full content in data layer events:** the log would grow large and could hold secrets. The digest still proves which version a step saw.
- **Attempt folders as `attempts/<step>/<n>/`:** awkward to read, and it does not show run order in a graph with cycles.
- **Any process may write (for example cancel or crash markers):** writes can mix or arrive in the wrong order, and a replay can then build the wrong state.
- **Delete runs by age automatically:** saves a command, but deletes the only record of a run nobody asked to lose. `prune --older-than` gives the same result when someone asks for it.
- **No `--force` flag on `remove`:** Loopfile could never destroy uncommitted work, but git's refusal names `--force`, and the caller then has to find the workspace path and run `git worktree remove --force` by hand. The flag was added after that hint misled a user.
- **Leave removal to the caller:** the caller would have to know the run folder layout and that an isolate worktree is registered in the Target folder's repository, where `rm -rf` leaves a stale worktree that still holds the run branch.
- **XDG and Application Support paths:** a different path on each platform is harder to document and harder for supervising agents to find.
